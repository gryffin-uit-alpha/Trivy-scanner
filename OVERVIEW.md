# Image Vulnerability Reporting — Overview

Nightly Azure DevOps pipeline scans every image our GitOps repositories deploy, and
turns the results into Markdown reports with day-over-day trends.

Split of responsibility: the **pipeline** does all orchestration (checkout, render,
registry auth, Trivy). The **Python application** does only business logic (parse,
count, compare, render). It never shells out to `git`, `kubectl`, `docker` or `trivy`,
never authenticates to a registry, and never reads the system clock — so identical
input always produces byte-identical reports.

## Flow

```
prepare ──┬─> scan_gitops-payments ──┐
          └─> scan_gitops-platform ──┴─> report ──> gate
```

| Job | Does |
| --- | --- |
| `prepare` | Stamps the scan date once (UTC) and warms the Trivy DB cache for the whole run. |
| `scan_<repo>` | Checks out the GitOps repo → `kubectl kustomize` the configured overlays → collect the image references they deploy → Trivy scan each image → publish one JSON per image. One job per repository; they are independent. |
| `report` | Merges the per-repository metadata, runs the Python application, publishes the Markdown reports and the rolling 90-day history. |
| `gate` | Reports the outcome. No severity threshold by default, so a nightly scan does not fail the build — the trend table is the signal. One variable enables gating if we want it later. |

Per image: `overlay → image reference → Trivy JSON → counts → report row + history entry`.

Two deliberate properties:

- **The gate is a separate job after `report`.** A threshold breach fails the build but
  cannot stop today's reports and history from being published. Without this, the first
  day a permanent CRITICAL appears would freeze the trend baseline forever.
- **A failed repository degrades coverage, not the run.** Other repositories still get
  their reports, and the missing one is listed as *unscanned* rather than looking clean.

Adding a GitOps repository is a configuration change in one pipeline file. No code change.

File names are fixed and date-free (`overall.md`, `repositories/gitops-payments.md`) so the
pipeline publishes from a static path. The date lives inside the document.

If a scan result is missing or unreadable, the report gains a **Failures** table naming the
file and the reason, and the run exits `2` — a visible gap instead of a silent one.

## Output 3 — history, one JSON per scan date

`history/2026-08-05.json` — the normalized counts, kept as a rolling 90-day archive.
This is the only thing the next run reads to compute trends.

```json
{
  "schema_version": 1,
  "scan_date": "2026-08-05",
  "images": [
    {
      "repository": "gitops-payments",
      "image_name": "registry.example.com/payments/api",
      "counts": { "critical": 1, "high": 2, "medium": 1, "low": 0, "unknown": 0 }
    },
    {
      "repository": "gitops-platform",
      "image_name": "registry.example.com/platform/ingress",
      "counts": { "critical": 0, "high": 1, "medium": 0, "low": 0, "unknown": 0 }
    }
  ],
  "repositories": [
    {
      "name": "gitops-payments",
      "subtotal": { "critical": 3, "high": 5, "medium": 5, "low": 1, "unknown": 0 }
    },
    {
      "name": "gitops-platform",
      "subtotal": { "critical": 0, "high": 1, "medium": 0, "low": 0, "unknown": 0 }
    }
  ],
  "unique_image_total":     { "critical": 3, "high": 6, "medium": 5, "low": 1, "unknown": 0 },
  "sum_of_subtotals_total": { "critical": 3, "high": 6, "medium": 5, "low": 1, "unknown": 0 },
  "shared_image_count": 0
}
```

- Counts only — no CVE identifiers, no package names, no image digests. Small, stable, and
  nothing sensitive in it.
- Keys sorted, so two identical scans produce byte-identical files.
- Stored as an Azure DevOps pipeline artifact. Each run downloads the previous archive, adds
  today's file, prunes anything older than 90 days, and republishes the whole directory.
- Re-running the same date replaces that date's file — no duplicates accumulate.
- If the previous archive is missing (first ever run), every count reports as `(new)` and the
  run still succeeds.

## Build result

| Exit | Meaning | Reports published? | Build |
| --- | --- | --- | --- |
| `0` | Ran clean | yes | green |
| `2` | Reports complete, but some scan results failed to parse | yes | green, with a warning naming the files |
| `1` | Could not run at all (bad config, missing manifest) | no | red |
| `3` | A configured severity threshold was met | yes | red — **not reachable by default** |

**No severity threshold is configured.** A daily report that turns the build red every
night — which is what happens from the first permanent CRITICAL onward — stops being
read, and the trend column is the signal we actually want. Blocking on severity belongs
on the path that ships an image, not on the one that observes it.

Enabling it later is one pipeline variable (`failOn: 'CRITICAL=1'`, or per severity such
as `'CRITICAL=1 HIGH=25'`). Reports and history are always published first, so a red
build never costs us the day's data.
